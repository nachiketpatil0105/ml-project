Patil Nachiket Kiran: data, features and errors

What I did. I checked the raw data, built the session split, wrote the feature code that turns the first half of a session into model inputs, wrote the leakage unit tests, did the error analysis, and built the website frame (menu, page loader, the Data, Preprocessing and Error analysis pages).

Key choices and why.

  • Split by session, not by row. Songs of one session share the same history. A row split would put half a session in training and the other half in testing, which makes the score look better than it is.
  • History = first ceil(L/2) songs. This follows the challenge description, so our target matches the published task. Odd-length sessions get one more history song.
  • Leave missing distances missing. If a listener kept no song in the first half there is no "kept profile". Filling in a number would hide that. The boosting libraries handle missing values directly.

How I checked it. validate() stops the pipeline if a session is incomplete, a position is repeated or a song has no features. A unit test changes the second-half answers of a session and checks that the features stay exactly the same. For errors, I broke the test accuracy down by queue position, by how mixed the first half was, by music source and by calibration.

A limitation I can explain. The re_* features (how history songs ended) are allowed, because they come from the first half, but a song that "played to the end" was by definition not skipped. So they partly repeat the skip history in another form. They do not leak the answer, but they make "history" look like several independent signals when it is mostly one.

Krish Kishor Patil: models, tuning and evaluation

What I did. I wrote the model, metric and cross-validation code, the Optuna search with repeated grouped cross-validation, the ablation and threshold check, the single final test with session bootstrap intervals, the in-browser explorer, and the "change one thing" script on this page.

Key choices and why.

  • Re-score the best five Optuna trials on three new fold splits. The best trial on one split is partly lucky. Choosing on 15 folds the search never used reduces that luck.
  • Tie rule of 0.001 MAA. Differences that small are far below the spread between folds. When two settings tie, the smaller model wins, and among libraries LightGBM wins because its trees can be exported to the browser.
  • Bootstrap over sessions, paired. Songs in a session depend on each other, so resampling rows would make the intervals too narrow. Pairing (same sessions for both models) makes model differences sharper.

How I checked it. Every choice was made on development data with 15 grouped folds. The test sessions were scored once, at the end. For each comparison I report the 95% interval of the paired difference and call a model better only if the interval is above zero.

A limitation I can explain. The settings search is not nested: the same development sessions were used to search and to estimate the score, so the development MAA is slightly optimistic. The gap between the development and test scores (Results page) is the honest check of that.
