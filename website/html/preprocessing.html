Preprocessing

From sessions to model inputs

Preprocessing means turning the raw tables into numbers a model can use. The most important rule: a row may only use things that would be known at the time of the prediction.

The steps, and why we do each one

  1. Check the data. We check that sessions are complete, that no song position is repeated, and that every song has its numeric features. Why: broken data can change results without anyone noticing. We never change the raw CSV files.
  2. Split by session. We split the sessions once, with a fixed random seed (42): development sessions (80%) and test sessions (20%). Why by session: songs in one session share the same history. If we split by row, the model would see part of a session in training and be checked on the rest, which is unfair.
  3. Cut each session into history and prediction window. The first K = ceil(L/2) songs are the history. The rest are predicted. An odd-length session rounds the history up, like the original challenge.
  4. Build features. We summarise the history and attach it, with the song's own numbers, to each song in the prediction window. This gives development rows and test rows. The answer (skip or not) is kept in a separate column and never used as an input.
  5. Fit transformations on training rows only. For the linear models and the random forest we fill missing values with the median, scale numbers, and one-hot encode category codes. These steps are learned inside each training fold only. Why: if validation rows influenced them, the check would be too optimistic. The boosting libraries handle missing values themselves and need no scaling.

The four feature groups

We keep the features in four groups so that we can later test what each group adds (the ablation on the Results page). The list of allowed input columns is also saved in python/02_preprocessing/results/feature_summary.json. Every model is checked against this list.

Missing values

If the listener kept no song in the first half (or skipped none), there is no "kept profile" (or "skipped profile") to compare with, so those distances are missing. We leave them missing instead of inventing a number, because a made-up distance would hide the fact that the profile does not exist.

How we stop data leakage

  • A unit test (python/02_preprocessing/test_features.py) changes the second-half answers of a session and checks that the features stay exactly the same. Another test checks the rounding rule for odd-length sessions.
  • The test sessions are not used to fit, tune or choose anything. They are scored once, at the very end (step 4).
  • History features read only the first K rows of a session.
  • We tried a "skip rate of each song across other sessions" feature. It did not help and would need extra care to be safe, so we dropped it.

Honest note: we made descriptive plots of the whole mini dataset (the Data page) before fixing the split. No model choice was made from those plots.
