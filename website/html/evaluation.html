Evaluation

How we keep the comparison fair

We fixed the split and the scores before comparing models. The test sessions stay untouched until the very end.

The split

  • sessions ( rows) are development data. We use them to train, tune and choose.
  • sessions ( rows) are the test set. We score each final model on it once.
  • The split is by session, so all songs of a session are on the same side.

Checking inside the development data (K-fold cross-validation)

  • K-fold. We cut the development sessions into 5 parts (folds). We train on 4 and check on the 5th, five times, so every part is used for checking once.
  • Grouped by session. A session is never split across folds.
  • Stratified. The folds have about the same share of skips, so no fold is easy or hard by chance.
  • Repeated. The search uses one fold split (seed ). The best candidates are scored again on three other fold splits (seeds 101, 102, 103). That makes 15 folds, and the final choice is made on their average. The development numbers in the results use these same repeated folds.
  • What this does and does not do. Cross-validation does not make a model more accurate. It makes our choice between models and settings more reliable. We did not use nested cross-validation because it is very slow. Instead, the final choice uses folds that the search did not use, which reduces (but does not remove) the chance that the search flatters the model.

The scores

  • MAA (main score). For one session we guess T songs. After each guess we compute the accuracy so far, and we count it only if that guess was right. AA is the average of these numbers. MAA is the average of AA over all sessions. A right guess early in the queue is worth more, because a streaming service acts on the next songs first. This is the score of the original challenge.
  • First-prediction accuracy. How often the very next song is guessed right.
  • ROC AUC. How well the model ranks skipped songs above kept songs. It does not depend on a threshold.
  • Accuracy. The share of all rows guessed right. We show it only for context. It is not our decision criterion.
A worked example of AA

A session with 5 guesses: right, right, wrong, right, right. The accuracy after each guess is 1, 1, 0.67, 0.75, 0.80. We keep only the values after right guesses: 1, 1, 0, 0.75, 0.80. The average is (1 + 1 + 0 + 0.75 + 0.80) / 5 = 0.71. If the wrong guess came first instead, AA would be lower, because the early guess counts more.

The decision threshold

Uncertainty on the test set

We draw sessions with replacement 2,000 times and recompute the score each time. The spread gives a 95% interval for each score and for the difference between two models, using the same sessions for both. If an interval for a difference includes zero, we cannot say the two models differ.

Why we resample sessions and not rows

Songs in one session depend on each other. Resampling rows would make the intervals too narrow.

How the test set was used (full disclosure)

While building the pipeline, we scored the test sessions once with an earlier version (first half = floor(L/2), small hand-picked settings). LightGBM scored 0.562 and copy last skip 0.531. After that we changed the first-half rule to match the original challenge, and we replaced the small settings grids with the Optuna search, because the first test result was modest. The search and every choice used development data only. The Results page shows the final pipeline scoring the same test sessions once. We tell you about the first run so you can see exactly how the test set was used.
